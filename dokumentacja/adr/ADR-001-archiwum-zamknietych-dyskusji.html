ADR-001 · DECYZJA ARCHITEKTONICZNA

Archiwum zamkniętych dyskusji i decyzji

Strona /dyskusje/ rozdziela rozmowy wymagające pracy od zakończonych spraw. Każda zamknięta dyskusja pozostaje w publicznym archiwum, a przyjęte rozstrzygnięcie prowadzi do właściwej karty decyzji regulaminowej.

STATUS: PRZYJĘTADATA: 17.09.2026OBSZAR: GITHUB PAGES I ACTIONS

← Katalog decyzji architektonicznych

Kontekst

Publiczna strona posiadała wyłącznie listę „Otwarte dyskusje”. Workflow Release pobierał z GitHub GraphQL tylko stan OPEN, a generator zapisywał jeden snapshot _data/open_discussions.json. Nie istniał model danych ani widok dla spraw zamkniętych.

Problem ujawniła dyskusja #19. Publiczny snapshot został utworzony 16.09.2026 o 19:45:12Z, a dyskusja została zamknięta trzy sekundy później, o 19:45:15Z. Release uruchomiony po scaleniu PR pobrał jeszcze otwarty stan. Samo wywołanie GraphQL closeDiscussion nie spowodowało kolejnej publikacji, a cykliczny harmonogram nie zapewnił natychmiastowej korekty strony.

Decyzja

Przechowujemy i publikujemy wszystkie zamknięte dyskusje. Rozstrzygnięte pokazują powiązaną decyzję regulaminową. Porzucone, duplikaty oraz zamknięte bez karty pozostają widoczne z właściwym statusem.
  1. Release pobiera dyskusje kategorii zmian regulaminu w stanach otwartym i zamkniętym.
  2. Jeden snapshot _data/discussions.json zawiera wspólny czas synchronizacji oraz osobne kolekcje open_items i closed_items.
  3. Jedynym kryterium sekcji otwartej jest brak closedAt. Etykieta nie może utrzymać zamkniętej dyskusji na liście otwartej.
  4. Jekyll łączy zamkniętą dyskusję z kartą w _decyzje przez dokładną zgodność adresu discussion_url.
  5. Workflow zamykający dyskusję jawnie uruchamia Release po skutecznym closeDiscussion. Harmonogram pozostaje zabezpieczeniem, ale nie jest podstawowym mechanizmem aktualizacji.

Przepływ danych

1. GitHub DiscussionsGraphQL zwraca oba stany, closedAt, etykiety i metadane kart.
2. Normalizacjasync_discussions.py filtruje kategorię i rozdziela wpisy według stanu.
3. PowiązanieJekyll porównuje URL dyskusji z discussion_url decyzji.
4. Publikacja/dyskusje/ pokazuje dwie sekcje z jednym czasem synchronizacji.

Kontrakt danych

Każdy wpis zachowuje numer, tytuł, URL, autora, datę utworzenia, liczbę wypowiedzi i etykiety oraz otrzymuje closed_at. Snapshot zawiera:

  • generated_at — wspólny czas synchronizacji;
  • open_items — wpisy bez closedAt, od najnowszych;
  • closed_items — wpisy z closedAt, od ostatnio zamkniętych.

Synchronizacja pobiera całą dostępną listę przez paginację GraphQL. Nie wolno bez ostrzeżenia ograniczyć archiwum do pierwszych 100 wpisów.

Dyskusja #19 stanowi przypadek regresyjny: występuje wyłącznie w sekcji zamkniętej, ma status „Przyjęta” i prowadzi do DR-001.

Publikacja i uprawnienia

Po dodaniu komentarza z linkiem do opublikowanej decyzji oraz skutecznym zamknięciu wątku resolve-discussion.yml uruchamia pages.yml na gałęzi main. Workflow zamykający otrzymuje ograniczone uprawnienie actions: write; pozostałe uprawnienia nie są rozszerzane.

Harmonogram nie daje gwarancji czasu: GitHub może opóźniać cykliczne uruchomienia. Harmonogram służy do samonaprawy ewentualnego rozjazdu, a jawny dispatch zapewnia aktualizację po decyzji.

Obsługa błędów

  • Błąd pobrania albo normalizacji przerywa build. Poprzednia poprawna wersja GitHub Pages pozostaje opublikowana.
  • Zamknięta dyskusja bez karty nadal pojawia się w archiwum; widok nie tworzy fałszywego linku.
  • Nierozpoznana etykieta daje neutralny status „Zamknięta”.
  • Błąd jawnego uruchomienia Release powoduje widoczny błąd workflow zamykającego. Harmonogram może później naprawić publikację.

Weryfikacja

  1. Test normalizatora rozdziela mieszany payload, zachowuje etykiety i sortuje zamknięte po closed_at.
  2. Test workflow wymaga obu stanów, pola closedAt, paginacji oraz dispatchu Release po zamknięciu.
  3. Test szablonu wymaga obu sekcji, statusów i powiązania przez discussion_url.
  4. Pełne testy Python i bundle exec jekyll build --strict_front_matter muszą przejść przed scaleniem.
  5. Kontrola produkcyjna potwierdza, że #19 jest wyłącznie w archiwum i prowadzi do DR-001.

Konsekwencje

Pozytywne

  • Lista otwartych pokazuje wyłącznie sprawy wymagające działania.
  • Historia dyskusji nie znika po zamknięciu.
  • Użytkownik przechodzi bezpośrednio od dyskusji do formalnej decyzji.
  • Publikacja nie zależy wyłącznie od opóźnianego harmonogramu.

Koszty i ograniczenia

  • Release wykonuje większe zapytanie GraphQL i musi obsłużyć paginację.
  • Workflow zamykający potrzebuje uprawnienia actions: write.
  • Dokładne powiązanie wymaga poprawnego discussion_url w karcie decyzji.
