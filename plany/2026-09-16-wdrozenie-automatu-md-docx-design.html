Bezpieczny automat Markdown → DOCX

Wdrożenie ustanawia kontrolowany Markdown jako źródło aktualnej treści, zachowuje zatwierdzony DOCX w każdym PR oraz daje Redaktorowi gotową propozycję zmiany bez ręcznego tworzenia dodatkowej migawki.

Granice i niezmienne zasady

Potwierdzone: kandydat /Users/aleks/coding/regulamin-candidate.docx został ręcznie sprawdzony w Microsoft Word. Próba parytetu pozostaje dowodem technicznym, a kontrola Worda domyka wymaganą bramkę wizualną.
  • Nie zmieniamy celu Regulaminu ani zatwierdzonego brzmienia bez odrębnej decyzji.
  • Nie usuwamy historycznych skryptów apply_approved_*.py.
  • Automat nigdy nie scala PR ani nie nadpisuje aktualnego DOCX po nieudanym buildzie.
  • Każda zmiana treści ma wspólny PR: karta decyzji, Markdown i rzeczywiście wygenerowany DOCX.

Etap 1 — ustanowienie źródła i bramki CI

  1. Dodać asercje akceptacyjne dla builda do jawnej ścieżki CI, testów kandydata, raportu parytetu i artefaktu.
  2. Pokazać RED, następnie dodać najmniejszy workflow oraz skrypt pomocniczy, jeśli będzie potrzebny.
  3. Wygenerować kandydat z Markdown; dopiero po wszystkich zielonych bramkach zastąpić wersję roboczą regulamin/..._2026.docx w tym samym PR.
  4. CI porównuje znormalizowaną treść i układ niezależnego kandydata z DOCX śledzonym w PR. Każdy przyszły PR musi więc aktualizować Markdown i wygenerowany DOCX razem.
Ochrona poprzedniej wersji: przed scaleniem poprzedni poprawny DOCX pozostaje na main. Nieudany workflow nie może wypchnąć ani zastąpić pliku; kandydat istnieje tylko w przestrzeni roboczej i jako artefakt runu.

Etap 2 — szybka ścieżka redakcyjna

Etykieta redakcja-bez-zmiany-sensu jest sygnałem Koordynatora. Aby automat był deterministyczny i nie zgadywał normatywnego brzmienia, formularz dyskusji zawiera dokładnie dwa pola: fragment Markdown do zastąpienia oraz nowe brzmienie Markdown.

  • Skrypt przyjmuje wyłącznie fragment występujący dokładnie raz; brak albo wielokrotne wystąpienie zatrzymuje automat z czytelną informacją w dyskusji.
  • Workflow tworzy albo bezpiecznie aktualizuje gałąź przypisaną do numeru dyskusji, tworzy kartę DR i draft PR.
  • Przed pushnięciem uruchamia generator, testy, parytet i kontrolę bezpieczeństwa; do PR trafiają Markdown i wygenerowany DOCX, a opis PR linkuje run i jego artefakt.
  • W decyzji pozostaje identyfikowalna decyzja i skutek. Szybka ścieżka nie wymaga rozbudowanego uzasadnienia ani listy wariantów.

Dwie ścieżki pracy komisji

Obie ścieżki kończą się tym samym bezpiecznym punktem: jednym PR zawierającym kartę decyzji, Markdown, wygenerowany DOCX i zielone bramki CI. Kluczowa różnica dotyczy odpowiedzialności za treść: w pełnej ścieżce Redaktor opracowuje brzmienie przepisu na podstawie decyzji komisji, a w szybkiej automat wykonuje dokładnie wskazaną korektę, która nie może zmienić sensu.

Gdzie zapada decyzja o DOCX

PR jest bramką człowieka. CI udostępnia artefakt regulamin-candidate.docx i DOCX śledzony w PR. Redaktor otwiera plik w Wordzie, następnie wybiera Approve i Merge, albo Request changes/zamyka PR. W drugim przypadku main i jego aktualny DOCX nie zmieniają się.

Release nie otrzymuje osobnego przycisku „Approve/Odrzuć”. Jest wyzwalany po scaleniu i publikuje wersję już zaakceptowaną w PR. Bramka środowiska w Release byłaby pozorna: mogłaby zatrzymać publikację Pages, ale nie cofnęłaby dokumentu, który po scaleniu już znajduje się w main.

  • Pełne testy repozytorium oraz testy bezpośrednio na nowo wygenerowanym DOCX.
  • docx_parity.py, compileall i git diff --check.
  • Testy idempotencji: ponowne oznaczenie tej samej dyskusji nie tworzy drugiej gałęzi, karty ani PR.
  • Testy odmowy: niejednoznaczna zamiana Markdown i nieudany build nie zmieniają śledzonego DOCX.
