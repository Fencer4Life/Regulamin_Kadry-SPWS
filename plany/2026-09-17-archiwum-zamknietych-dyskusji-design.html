Archiwum zamkniętych dyskusji i decyzji

Strona /dyskusje/ ma rozdzielać rozmowy wymagające pracy od zakończonych spraw. Każda zamknięta dyskusja pozostaje w publicznym archiwum, a przyjęte rozstrzygnięcie prowadzi bezpośrednio do właściwej karty decyzji.

Zatwierdzona zasada: archiwum obejmuje wszystkie zamknięte dyskusje. Rozstrzygnięte pokazują powiązaną decyzję; porzucone i duplikaty pozostają widoczne bez wymogu tworzenia decyzji.

Problem potwierdzony na dyskusji #19

Publiczny snapshot został utworzony 16.09.2026 o 19:45:12Z, a dyskusja #19 została zamknięta o 19:45:15Z. Release rozpoczęty po scaleniu PR zdążył więc pobrać jeszcze otwarty stan. Zdarzenie zamknięcia nie uruchomiło kolejnej publikacji, a harmonogram GitHub Actions nie wykonał następnej synchronizacji w deklarowanym odstępie.

Obecna implementacja dodatkowo pobiera wyłącznie dyskusje OPEN i generuje jedną listę open_discussions. Nie posiada modelu danych ani widoku dla spraw zamkniętych.

Architektura i przepływ danych

1. GitHub DiscussionsRelease pobiera dyskusje kategorii zmian regulaminu w stanach otwartym i zamkniętym, wraz z closedAt i etykietami.
2. Normalizacjasync_discussions.py filtruje kategorię oraz tworzy open_items i closed_items.
3. PowiązanieJekyll zestawia URL zamkniętej dyskusji z polem discussion_url w kolekcji _decyzje.
4. Publikacja/dyskusje/ pokazuje dwie osobne sekcje i aktualny czas synchronizacji.

Kontrakt snapshotu

Plik danych otrzyma neutralną nazwę _data/discussions.json. Zachowa pola obecnych kart i doda closed_at. Najwyższy poziom będzie zawierał:

  • generated_at — wspólny czas wykonania synchronizacji;
  • open_items — tylko wpisy bez closedAt, od najnowszych;
  • closed_items — tylko wpisy z closedAt, od ostatnio zamkniętych.

Synchronizacja obejmie całą dostępną listę, a nie tylko przypadkowy pierwszy fragment danych. Dzięki temu archiwum nie zacznie po cichu gubić najstarszych wpisów po przekroczeniu limitu pojedynczej strony GraphQL.

Widok strony

Otwarte dyskusje

Pierwsza sekcja zachowa dzisiejszą formę i przycisk otwarcia nowej dyskusji. Dyskusja z ustawionym closedAt nie może zostać wyrenderowana w tej sekcji, niezależnie od etykiety.

Natychmiastowa synchronizacja po decyzji

Workflow resolve-discussion.yml, po dodaniu komentarza i skutecznym wywołaniu closeDiscussion, jawnie uruchomi workflow pages.yml na gałęzi main. Wymaga to ograniczonego uprawnienia actions: write tylko w workflow zamykającym.

Dlaczego nie wystarcza harmonogram: GitHub Actions może opóźniać lub pomijać uruchomienia cykliczne przy obciążeniu. Harmonogram pozostaje mechanizmem naprawczym, ale nie będzie jedynym sposobem usunięcia zamkniętej dyskusji z listy otwartych.

Obsługa błędów

  • Jeżeli pobranie dyskusji lub normalizacja nie powiedzie się, build Release kończy się błędem, a poprzednia poprawna wersja GitHub Pages pozostaje opublikowana.
  • Zamknięta dyskusja bez pasującej karty nadal pojawia się w archiwum. Widok nie tworzy fałszywego linku ani nie ukrywa wpisu.
  • Nierozpoznana etykieta daje neutralny status „Zamknięta”; automat nie zgaduje wyniku merytorycznego.
  • Nieudane jawne uruchomienie Release powoduje błąd workflow zamykającego, dzięki czemu problem jest widoczny w Actions; cykliczna synchronizacja pozostaje zabezpieczeniem.

Testy i kryteria odbioru

  1. Test normalizatora najpierw na czerwono: mieszany payload trafia do dwóch list, zachowuje etykiety, a zamknięte sortują się po closed_at.
  2. Test kontraktu workflow: zapytanie pobiera oba stany i pole closedAt; workflow zamykający uruchamia Release dopiero po zamknięciu.
  3. Test szablonu: strona zawiera obie sekcje, statusy i powiązanie przez discussion_url.
  4. Pełny zestaw testów Python oraz bundle exec jekyll build --strict_front_matter przechodzą lokalnie i w CI.
  5. Po wdrożeniu strona publiczna pokazuje #19 wyłącznie w „Zamkniętych dyskusjach i decyzjach”, ze statusem „Przyjęta” i działającym linkiem do DR-001.
