Kolejność wdrożenia

1. Testy RED — kontrakt danych

  1. Rozszerzyć fixture o otwarte i zamknięte dyskusje, różne kategorie, etykiety oraz dwie strony odpowiedzi GraphQL.
  2. Oczekiwać jednego wyniku z generated_at, open_items i closed_items.
  3. Wymagać sortowania otwartych po created_at malejąco, a zamkniętych po closed_at malejąco.
  4. Uruchomić test i zachować wynik RED wynikający z braku nowego kontraktu.
python3 -m unittest tests.test_discussions -v

2. Testy RED — strona i workflow

  1. Wymagać w dyskusje.html nagłówków obu sekcji, użycia site.data.discussions, stanów „Przyjęta”, „Porzucona”, „Duplikat”, „Zamknięta” oraz dopasowania discussion_url.
  2. Wymagać, aby nawigacja liczyła open_items, a nie stary snapshot.
  3. Wymagać w Release parametrów states:[OPEN,CLOSED], pola closedAt, pageInfo, zmiennej endCursor, opcji --paginate --slurp i nowej ścieżki danych.
  4. Wymagać w workflow zamykającym actions: write oraz gh workflow run pages.yml --ref main umieszczonego po closeDiscussion.
  5. Uruchomić testy i potwierdzić RED.
python3 -m unittest tests.test_registry_platform -v

3. Implementacja normalizatora i migracja snapshotu

  1. Przyjąć zarówno pojedynczy obiekt GraphQL, jak i tablicę stron zwróconą przez gh api --slurp.
  2. Iterować po wszystkich nodes, zachować wyłącznie kategorię propozycje-zmian-regulaminu i zbudować wspólny rekord z closed_at.
  3. Podzielić rekordy wyłącznie według obecności closedAt. Etykiety nie sterują przynależnością do listy.
  4. Zapisać pusty kontrakt w _data/discussions.json i usunąć stary plik dopiero po usunięciu wszystkich odwołań.
  5. Uruchomić test danych do GREEN.

4. Widok dwóch sekcji

  1. Zachować hero i przycisk otwarcia dyskusji.
  2. Wyrenderować open_items w sekcji „Otwarte dyskusje”.
  3. Wyrenderować closed_items w sekcji „Zamknięte dyskusje i decyzje”.
  4. Dla każdego zamkniętego wpisu wyznaczyć publiczny status z etykiet zgodnie z ADR-001.
  5. Przeszukać site.decyzje i pokazać „Zobacz decyzję DR-NNN” tylko przy dokładnej zgodności discussion_url. Brak karty nie ukrywa dyskusji.
  6. Zaktualizować licznik nawigacji do site.data.discussions.open_items.size.

5. Paginowane pobieranie w Release

Zapytanie GraphQL użyje first:100, after:$endCursor, obu stanów oraz pageInfo { hasNextPage endCursor }. gh api graphql --paginate --slurp zapisze wszystkie strony w jednym pliku wejściowym dla normalizatora.

Warunek bezpieczeństwa: brak paginacji jest błędem kontraktu. Archiwum nie może po cichu tracić starszych dyskusji po przekroczeniu 100 rekordów.

6. Natychmiastowy Release po zamknięciu

  1. Dodać tylko actions: write do resolve-discussion.yml.
  2. Po udanym closeDiscussion wykonać gh workflow run pages.yml --ref main.
  3. Nie dispatchować Release przed zamknięciem, aby nie powtórzyć wyścigu z #19.
  4. Zachować harmonogram jako mechanizm okresowego uzgadniania stanu.

7. Walidacja lokalna

  1. Uruchomić najpierw dwa zmienione moduły testowe, potem pełny zestaw.
  2. Uruchomić kompilację Python i sprawdzenie białych znaków.
  3. Zbudować Jekyll z rygorystyczną kontrolą front matter. Jeżeli lokalny Bundler nadal jest niedostępny, nie instalować zależności bez zgody; odnotować brak i oprzeć końcową bramkę na CI.
  4. Sprawdzić pełny diff oraz upewnić się, że nie zmieniono treści regulaminu ani DOCX.
python3 -m unittest tests.test_discussions tests.test_registry_platform -v
python3 -m unittest discover -s tests -v
python3 -m compileall -q narzedzia tests
git diff --check
bundle exec jekyll build --strict_front_matter

8. PR, CI i publikacja

  1. Zacommitować implementację na istniejącej gałęzi codex/closed-discussions-archive i wypchnąć ją dopiero po przeglądzie kompletnego diffu.
  2. Utworzyć PR obejmujący trzy commity dokumentacyjne i implementację.
  3. Obserwować CI do końca; w razie błędu pobrać log właściwego kroku i naprawić przyczynę.
  4. Po scaleniu obserwować Release do sukcesu.
  5. Otworzyć publiczne /dyskusje/ i potwierdzić trzy fakty: #19 nie ma w otwartych, #19 jest w zamkniętych, link prowadzi do DR-001.
  6. Otworzyć publiczny katalog /dokumentacja/adr/ i potwierdzić dostępność ADR-001.

Ryzyka i cofnięcie

  • Niepoprawna składnia GraphQL: zatrzyma Release przed deployem; poprzednia strona pozostanie aktywna.
  • Brak decyzji dla zamkniętego wpisu: archiwum pokaże dyskusję bez linku zamiast ją ukrywać.
  • Błąd dispatchu: workflow zamykający będzie czerwony, a harmonogram pozostanie drogą samonaprawy.
  • Cofnięcie: revert commita implementacyjnego przywróci poprzedni snapshot i widok; commity ADR pozostaną historią przyjętej decyzji, chyba że decyzja zostanie zastąpiona nowym ADR.

  • Release zakończył się sukcesem.
  • #19 jest publicznie widoczna tylko jako zamknięta i prowadzi do DR-001.
  • Nowe zamknięcie dyskusji uruchamia Release po zmianie stanu.
  • ADR-001 i jego indeks są dostępne w GitHub Pages, a najnowszy ADR pozostaje na górze listy.
