Regulamin Kadry SPWS · Implementation Plan · 27.09.2026

Dwa regulaminy, jeden kontrolowany proces

Najpierw wielodokumentowy fundament i testy, potem formularze oraz publikacja, następnie dopracowane diagramy, a dopiero na stabilnym automacie pełna redakcja Regulaminu Współzawodnictwa i spójna zmiana Regulaminu Reprezentacji.

Projekt: zatwierdzony TDD: obowiązkowe Ruff: obowiązkowy 1 decyzja = 1 PR = 1 wydanie

1. Wynik końcowy i kolejność zależności

1. FundamentRejestr JSON, Ruff i obsługa dwóch dokumentów.
2. ProcesDwa formularze, wspólna karta i atomowa zmiana.
3. PrezentacjaRole, etykiety, filtry i piękne diagramy.
4. TreśćDwa zgodne regulaminy i Klasyfikacja łączona.
5. WydanieDwa DOCX, pełne CI, Word i odbiór wizualny.
Treść nie wyprzedza automatu.

Najpierw testy bieżącego kontraktu DOCX, rejestr dokumentów i bezpieczne budowanie kandydatów. Dzięki temu błędu generatora nie pomylimy z błędem redakcji nowego regulaminu.

2. Docelowa architektura

ElementJedno źródło prawdyOdpowiedzialność

Dlaczego JSON.

Python czyta go biblioteką standardową, Jekyll bezpośrednio przez site.data, a Git wersjonuje konfigurację razem z kodem i regulaminami. Nie powstaje zewnętrzny stan, sekret ani zależność od dostępności PostgreSQL.

3. Kontrakt danych decyzji

Nowa karta otrzymuje schema_version: 3, pole dokumenty z wartościami reprezentacja i/lub zawody oraz wynik przyjęta albo odrzucona. Decyzja procesowa ma pustą listę dokumentów.

schema_version: 3
status: przyjęta
dokumenty:
  - reprezentacja
  - zawody

## Wpływ na spójność dokumentów
...

## Zmiana — Regulamin Reprezentacji
### Stary fragment Markdown
...
### Nowy fragment Markdown
...

## Zmiana — Regulamin Zawodów
...
  • status: odrzucona tworzy i publikuje kartę, lecz nie dopuszcza zmiany Markdown ani DOCX.
  • Karty wersji 1 i 2 zachowują dotychczasowe znaczenie i są interpretowane jako dotyczące Reprezentacji.
  • Automat mapuje pola dosłownie; nie streszcza komentarzy i nie tworzy brakującego przepisu.

6. Granice i operacje wymagające osobnej zgody

  • Utworzenie na GitHubie drugiej kategorii Discussions o slugu zgodnym z nazwą formularza jest operacją administracyjną; przed zmianą zostanie pokazany dokładny slug.
  • Zmiana uprawnień GitHub Actions, utworzenie PR, scalenie, wydanie i zamknięcie rzeczywistej dyskusji nie wynikają automatycznie z tego planu.
  • Źródłowy PDF i strona SPWS pozostają nietknięte.
  • Nie dodajemy serwera PostgreSQL ani nowej zależności produkcyjnej.
  • Automatyczne testy spójności nie zastępują przeglądu Komisji, kontroli prawnej ani sprawdzenia DOCX w Wordzie.

7. Definicja ukończenia

  • rejestr zawiera dwa poprawne dokumenty i jest jedynym źródłem ich ścieżek;
  • oba formularze tworzą poprawne karty schema 3;
  • jedna decyzja może bezpiecznie zmienić jeden albo oba dokumenty;
  • Ruff, pełne testy, Jekyll oraz build i verify obu DOCX są zielone;
  • oba regulaminy są zgodne z ZTP i przechodzą testy wspólnych pojęć, celu i reguł;
  • Klasyfikacja łączona dotyczy wyłącznie pierwszej rundy grupowej PPW i indywidualnych MPW;
  • przewodnik, Zasady Rejestru, formularze i workflowy opisują jeden proces oraz właściwe role;
  • wszystkie cztery diagramy przeszły ręczny odbiór desktop/mobile i light/dark;
  • oba DOCX zostały otwarte i zaakceptowane w Microsoft Word;
  • draft PR zawiera czytelne linki do obu kandydatów i nie jest automatycznie scalony.
